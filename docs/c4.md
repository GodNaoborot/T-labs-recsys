# Прогноз следующего временного пакета

Здесь проверяю признаки после изменения времени запроса. Раньше эта граница
восстанавливалась из текущей доли прослушивания и могла передавать информацию
о метке. Теперь беру её из прошлого журнала пользователя.

Сначала сравнил исходные ручные, расширенные ручные и автоматические DFS-признаки. Затем добавил контроль расширенного ручного набора без текущего канала взаимодействия.
[Результаты test](c4-test.md), [общий итог](../README.md).
В файлах протокол обозначен `C4`, модели — `M-t`, `C2b-t`, `D462-t`.

## Время запроса и история

Для каждого пользователя объединяю listen с одинаковым исходным timestamp
в один пакет. Для следующего пакета время запроса `t` равно предыдущему
строго меньшему timestamp. Все строки целевого пакета получают один `t`.
В историю входят только события с `timestamp < t`, а окна имеют вид
`[t-window, t)`. Предыдущий пакет прямо на границе `t` тоже исключён.

Первый пакет не используется. Пакеты строятся до разбиения и фильтров;
старый start_ts не подставляется вместо отсутствующего запроса.
При одинаковом времени исторические строки упорядочены по неизменному
физическому ID источника; порядок внутри пятисекундного бина неизвестен.

## Метки и выборки

Правила меток и привязки реакций остаются прежними: берётся ближайшее
следующее окончание той же пары с проверкой восстановленного интервала.
Like имеет приоритет над dislike. Если любой привязанный к целевому listen
like/dislike произошёл раньше `t`, строка исключается независимо от итогового
label. Unlike и undislike метку не задают.

Cutoff берётся из прошлого журнала, а разметка и отбор сохраняют
прежнюю привязку реакций.

| Часть | Время запроса | Дополнительное условие |
| --- | --- | --- |
| Train | `225*DAY <= t < 270*DAY` | Конец target строго раньше `270*DAY-1800` |
| Validation | `270*DAY <= t < 285*DAY` | Конец target строго раньше `285*DAY-1800` |

Все компоненты метки должны быть доступны к указанной границе. Причины
исключений, пересечения и состав меток сохраняются в отчёте подготовки.

Группа задаётся как `uid*1000 + floor(t/DAY)`. После нового разбиения
постоянные по label группы удаляются. Из train выбираются 40 000 целых
смешанных групп без замены с seed 42. Validation содержит все допустимые
смешанные группы. Строки, метки, дни, группы и их порядок одинаковы для моделей.

## Признаки и модели

| Вариант | Активные входы |
| --- | --- |
| Исходные ручные с текущим `is_organic` | 42 ручных признака, пересчитанных относительно t |
| Расширенные ручные с текущим `is_organic` | Те же 42 и 7 признаков общей истории пользователя |
| Расширенные ручные без текущего канала | Те же входы, кроме текущего `is_organic`: 48 активных из 49 физических |
| Автоматические DFS | Зафиксированные 462 формулы, пересчитанные относительно t |

Текущие played_ratio, label и восстановленный start_ts в X не входят.
Список DFS не переотбирается. Пороги CatBoost обучены заново только
на общей train-подвыборке; validation использует их без изменений.

Все четыре модели: YetiRank, depth 6, learning_rate 0.1, seed 42,
до 1600 деревьев, early stopping 80 и четыре потока. Параметры перенесены
из прежних контролей и записаны до первого fit.

Для трёх последовательных обучений использовался общий лимит 7200 секунд,
включая загрузку и оценку моделей. Подготовка данных и признаков учитывалась
отдельно. Матрицы рассчитывались порциями, чтобы ограничить расход памяти.

## Оценка

Использую линейный NDCG@10 и QueryAUC Ranking. Точные ничьи во внешнем NDCG
разрешаются общей перестановкой с seed 42. Заранее выбраны три сравнения:
DFS с исходными ручными, расширенные ручные с исходными и расширенные ручные
с DFS.

Парный циклический блочный bootstrap берёт календарные блоки по 3 и 4 дня:
20 000 реплик, seed 42, двусторонние 95% percentile-интервалы.
Вес user-day групп сохраняется. Поправки на множественные сравнения нет.
Validation и выбранные формулы уже использовались в исследовании,
поэтому интервалы остаются условными на готовых моделях и прежнем выборе.

User-day объединяет наблюдавшиеся события с разными моментами запроса.
Смысл timestamp и доступность полей остаются допущениями, test уже открывался.
После изменения времени изменились также строки и история, поэтому
старые и новые метрики не образуют парного сравнения.

## Запуск

Из корня проекта с активной средой:

```bash
python task_1/src/run_c4.py --run-name c4_repeat01 --max-training-seconds 7200
python task_1/src/run_c4.py --run-name c4_packet_20261024_v1 --status
```

Перед обучением нужна подготовленная история. Полный путь описан в
[инструкции воспроизведения](reproduction.md).
Данные нового запуска лежат в `task_1/data/c4/<имя>/`, отчёты и модели
в `task_1/results/c4/<имя>/`. Протокол и исходники фиксируются до запуска.

## Результаты

При подготовке перепроверены 43 053 080 сохранённых меток до 285-го дня.
Они совпали с разметкой по исходным реакциям.

Получилось 2 021 867 train-строк / 40 000 групп и 2 879 535 validation-строк
/ 57 097 групп. Ранние привязанные like/dislike отмечены у 448 назначенных
train-строк и 170 validation-строк. Пересечения с GAP записаны в exclusions.json.

| Модель | Validation NDCG@10 |
| --- | ---: |
| Исходные ручные с текущим `is_organic` | 0.768964 |
| Расширенные ручные с текущим `is_organic` | 0.804896 |
| Расширенные ручные без текущего канала | 0.804589 |
| Автоматические DFS | 0.804623 |

Первоначальные три модели вместе с подготовкой заняли 67.04 минуты, пик anonymous RAM 5.745 GiB.
Сравнения и интервалы сохранены в comparison.csv и bootstrap_summary.csv.
Те же модели оценены на [test](c4-test.md).

Границы истории, совпадающие timestamp и привязка реакций проверены
на небольших примерах. На фактических запросах значения признаков
сверены с отдельным pandas-пересчётом.

## Контроль без текущего канала

В ручные 42/49 попадал `is_organic` из будущей целевой строки. Его доступность
в момент запроса не обоснована. Поэтому для отдельного контроля исключён
только этот столбец: осталось 48 активных входов, исторические значения
`is_organic` сохранены. Контроль 41 входа для исходной ручной модели не проводился.

Основная пара «ручные 48 — DFS462» выбрана после открытия test по причине
необоснованной доступности текущего канала. Это дополнительное исследовательское
сравнение, а не подтверждение заранее выбранной пары на закрытом test.

Модель обучена в отдельной аудиторской копии исходной версии `472be9e`.
Строки, метки, группы, train-пороги, параметры и seed совпадают с прежним
сравнением. Новый подбор параметров и отбор формул не выполнялись.
Готовые результаты перенесены в
[no_current_channel](../task_1/results/c4/no_current_channel/result.json);
готовая модель хранится локально и не входит в Git. Исходные скрипты:
[обучение](../task_1/reproduction/channel_control_fit.py),
[оценка](../task_1/reproduction/channel_control_evaluate.py).

На validation ручные 48 получили NDCG@10 **0.804589** против **0.804623** у DFS.
Разница составила **−0.000034**. Парные интервалы для ручных 48 − DFS:
блок 3 дня — **[−0.001220; +0.001134]**, блок 4 дня — **[−0.001171; +0.001101]**.
Они включают ноль, но не устанавливают эквивалентность методов.

Результат после исключения поля снизился относительно ручных 49 на 0.000306.
Обучение заняло 1070.33 секунды и сохранило 911 деревьев. Оно шло с пониженным
приоритетом параллельно другим аудиторским расчётам; время нельзя напрямую
сравнивать с прежними fit. [Протокол](../task_1/results/c4/no_current_channel/protocol.json)
и [интервалы](../task_1/results/c4/no_current_channel/bootstrap_summary.csv).
